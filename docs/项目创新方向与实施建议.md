# 人脸识别考勤系统：使用体验创新方案

## 一、建议围绕什么做创新

这个项目最值得做的体验创新，是让系统在每个关键时刻告诉用户：**现在该做什么、刚才是否成功、遇到问题怎么继续。**

员工日常面对的是“完成打卡”“看懂异常”“处理漏卡”几件事；管理员面对的是“让新人顺利用起来”“快速核查申请”。围绕这些任务重新组织交互，可以让项目形成鲜明的使用特色。

建议将体验主线确定为：

**打卡时有引导 → 结束后有明确回执 → 出现异常能直接处理 → 提交后能一路追踪。**

以下方案基于当前页面和业务流程提出，均为建议新增或深化的体验。

| 创新方向 | 用户能直接感受到的变化 | 建议优先级 |
| --- | --- | --- |
| 连续引导的轻操作打卡 | 进入页面就知道点哪里、做什么动作、还剩哪一步 | 第一批 |
| 失败后原地处理、结果明确可查 | 看见原因后直接解决，连接中断时也能确认结果 | 第一批 |
| 从异常记录直接办理补卡 | 日期和缺失类型自动带入，办理过程始终跟着原记录 | 第一批 |
| 以“今天”为中心的个人工作台 | 登录后先看到今天的状态和需要处理的事 | 第二批 |
| 带完整上下文的审批工作台 | 在一个地方看清申请、原记录和处理后的变化 | 第二批 |
| 新员工引导与局部补拍 | 按步骤完成首次使用，有一张没拍好就只补这一张 | 第二批 |

其中，**“连续引导打卡”和“异常记录直接办理”最适合作为核心体验亮点**。前者改善高频操作，后者把多个页面串成一条完整的办事流程。

## 二、创新一：连续引导的轻操作打卡

### 当前体验

公共打卡页已有签到、签退按钮、摄像头预览和分阶段文字提示。用户需要选择打卡类型，并在看着镜头的同时阅读提示、理解动作、判断是否完成。

可以进一步减少用户的选择和阅读负担，让整个过程像有人在旁边带着操作。

### 建议体验

**进入页面：优先展示此刻最相关的操作。**

根据服务器给出的当前打卡时段，突出“上班签到”或“下班签退”一个主按钮，并在按钮附近说明当前时段。其他入口按可用状态显示，测试模式保留明确的签到、签退选择。

公共页面根据时间和规则推荐操作；员工登录后的工作台还可以结合本人的当天记录提示下一步。

**开始采集：把调整建议放在视线集中的地方。**

摄像头画面附近显示一条最需要执行的提示，例如“请靠近一点”“保持单人入镜”。画面条件合适后，再进入动作引导，避免多条提示同时争夺注意力。

**执行动作：提供会动的示范和清晰步骤。**

在现有阶段文字基础上，增加简短动作示意与步骤状态，例如：

> 站好位置 ✓ → 正在完成眨眼 → 接下来按提示张嘴 → 确认结果

当前动作突出显示，已完成步骤收起。示意与服务端实际阶段同步；进度表现为完成了哪些步骤。员工可以选择语音引导，页面同时保留大字提示和静音入口，语音只播报操作。

**结束：给出清楚的完成感。**

确认入库后，显示“上班签到成功”和服务端确认的时间，配合短暂的视觉反馈。公共屏幕沿用身份信息短时展示，随后恢复为适合下一位使用的待机页面。

### 体验创新点

将“点按钮、读提示、猜进度”组织成一段连贯的引导过程。用户只需跟随当前一步，系统负责安排节奏。

### 演示方式

让第一次使用的人独立完成一次打卡，观察他是否还需要问“点哪个”“现在该做什么”“可以走了吗”。这三个问题的减少，就是最直观的体验变化。

## 三、创新二：失败后能原地处理，结果始终有着落

### 当前体验

系统已经区分摄像头权限、识别困难、连接中断等问题，也有断线后查询会话结果的处理。部分失败结果会进入三秒清除流程，随后用户重新选择操作。

可以把这些已有判断转化为更完整的恢复体验，让问题发生后，页面仍然带着用户往下走。

### 建议体验

**把失败提示做成可操作的处理卡。**

| 遇到的情况 | 页面呈现 | 主操作 |
| --- | --- | --- |
| 摄像头权限未开启 | 简短说明如何在当前浏览器允许摄像头 | 我已开启，重新检测 |
| 面部过暗或位置不合适 | 给出当前最需要调整的一项建议 | 调整好了，再试一次 |
| 动作没有完成 | 标出停在哪一步，提供该动作的示范 | 看示范后重新开始 |
| 设备暂时无法打卡 | 明确设备需要管理员处理，展示设备名称 | 查看处理指引 |
| 连接中断、结果待确认 | 显示“正在确认刚才的打卡结果” | 查询本次结果 |
| 服务器确认已打卡 | 展示实际结果和记录时间 | 完成 |

失败帮助保持可见，直到用户处理或退出。身份展示与帮助卡分别控制，公共设备仍按既有时限清除身份信息。

**重试时记住用户刚才的选择。**

保留签到或签退类型、静音偏好等操作上下文。点击重试直接开始一次新的验证，用户无需返回起点重新选择。

**把“结果待确认”单独呈现。**

断线后先查询原会话。查到已成功就补上回执；确认未完成后提供重新开始；暂时查不到时保持“待确认”，并给出继续查询与管理核查入口。

**在页面内保留结果核查路径。**

用户可以查询当前设备本次会话的结果；详细个人记录放在登录后的“我的考勤”中。持续识别困难时，提供清楚的管理员协助入口；后续符合补卡条件时，从个人记录接着办理。

### 体验创新点

让用户在失败后仍然知道下一步，并能分清“需要调整后重试”和“需要先确认结果”。这能减少盲目重复打卡和对系统结果的疑惑。

### 演示方式

分别演示摄像头权限关闭、光线不足和打卡过程中断网。观察用户能否在当前页面继续处理，以及是否能说清楚最终有没有生成记录。

## 四、创新三：从异常记录直接办理，一条记录跟进到底

### 当前体验

员工在考勤页看到缺卡后，需要进入“请假与补卡”、切换补卡页签、重新选择日期和类型，再填写时间与原因。申请提交后，办理状态主要在申请列表中查看。

这里最值得改善的是跨页面衔接：用户已经在一条具体记录上发现问题，系统可以直接从这条记录开始帮助他处理。

### 建议体验

以“昨天缺少签退”为例，新的流程可以是：

**看到缺签退 → 点击“补这次签退” → 填写实际时间和原因 → 原记录显示待审批 → 审批后原位查看结果。**

具体交互包括：

1. **让异常卡片直接成为办理入口。** 在本人符合补卡条件的记录旁显示“补签到”或“补签退”，按钮名称对应当前问题。
2. **自动带入已经明确的信息。** 带入日期、缺失类型，并展示当天已有打卡。实际补卡时间由本人填写，表单提示“你实际离开的时间”，帮助理解字段。
3. **在原页面展开办理。** 手机使用底部面板，电脑使用侧边面板。用户始终能看到正在处理哪一天的记录，提交后保持原筛选与浏览位置。
4. **让进度回到原记录。** 提交后原按钮变为“补签退待审批”；已有申请时直接进入进度，避免用户再次填写。
5. **将处理结果接回当天考勤。** 批准后显示有效签退和处理说明；驳回后展示原因，并提供“参考原申请重新填写”，方便用户补充事实后重新提交。

当天尚未签退显示为“今天还待完成”。次日确认缺卡且满足现有最近七日补卡条件时，再显示办理入口。

### 可以顺带做出的体验亮点

把一条考勤记录展开成简短时间线：

> 昨日 08:56：已签到  
> 昨日：缺少签退记录  
> 今日 09:10：提交补签退申请  
> 今日 10:20：申请获批，有效签退调整为昨日 18:06

时间线中的节点来自实际记录，并提供“为什么这样判定”的简短说明。用户在一个地方就能理解事件、处理过程和当前结果。

### 体验创新点

**让问题、办理入口、申请进度和最终结果始终围绕同一条记录。** 用户无需在多个功能页面之间记忆和搬运信息。

### 演示方式

从一条昨日缺签退记录出发，完成提交、审批和结果回看。对比办理过程中切换了多少页面、重复填写了多少信息，以及能否快速找到申请进度。

## 五、创新四：以“今天”为中心的个人工作台

### 当前体验

当前员工首页主要展示本月指标、图表和最近几条考勤。日常登录时，用户往往更关心今天是否已经签到、是否还需要签退，以及有没有事情需要处理。

### 建议体验

将首页从上到下安排为三个层次：

| 区域 | 展示内容 | 对应操作 |
| --- | --- | --- |
| 今天 | 已签到、待签退、今日已完成或已批准整天请假 | 查看当天记录、前往可用打卡入口 |
| 需要处理 | 近期可补卡异常、需要补充的申请 | 直接办理对应事项 |
| 最近进展 | 申请待审批、已批准、已驳回及简短原因 | 查看处理过程 |

月度统计放在这些内容之后，供需要回顾时查看。

一个员工首页可以这样呈现：

> **今天已于 08:56 签到**  
> 下班时记得签退。  
>   
> **有 1 件事需要处理**  
> 昨天缺少签退记录　［补这次签退］  
>   
> **最近进展**  
> 下周一的请假申请正在等待审批　［查看申请］

点击某个事项后，目标页面自动定位到对应日期、记录或申请；返回时保留原位置。当天未完成事项使用“待完成”，避免让员工过早理解为考勤异常。

提醒首先放在应用内，在登录或查看工作台时出现。已处理的事项及时从待办中移除，同一事项合并展示。

### 体验创新点

首页直接回答“今天怎么样、接下来做什么”。它将分散在考勤和申请页面里的信息组织成每个人自己的行动入口。

### 演示方式

让员工登录后，在不打开菜单的情况下回答三个问题：今天是否完成签到、有没有待处理异常、刚提交的申请进展如何。

## 六、创新五：带完整上下文的审批工作台

### 当前体验

管理员目前从申请列表进入审批弹窗，弹窗主要展示申请人和原因。核查当天记录、理解处理后的变化，需要结合其他页面的信息。

### 建议体验

把审批详情做成一张“完整办事卡”，同时呈现：

- **申请内容：** 谁申请、哪一天、补哪次卡、申请时间和原因。
- **当天事实：** 原有签到签退、相关请假和已处理补卡。
- **当前问题：** 例如缺签退，或已有签到需要修正。
- **处理后的变化：** 例如“批准后补齐签退；因申请时间为 17:30，仍会标记早退”。
- **操作区：** 核查意见、批准、驳回，以及处理后的“下一条”。

管理员可以保留当前筛选连续处理。遇到需要核实的申请，先跳到下一条；核查完再返回，仍能找到原来的位置。

员工侧同步收到可理解的结果：批准后说明哪条记录已更新；驳回后展示具体原因和后续入口。管理员与员工看到的是同一件事的不同视角。

### 体验创新点

将“搜集判断所需的信息”和“做出处理”放进同一处，缩短核查路径。同时让审批结果自然回到员工的原始问题上。

### 演示方式

连续处理两条补卡申请，其中一条补齐后正常，另一条补齐后仍早退。观察管理员是否能在审批面板内判断差异，员工能否理解处理结果。

## 七、创新六：新员工从建档到首次成功的引导流程

### 当前体验

人员建档、账号交付、人脸录入和打卡分别有入口。录入界面已有三张照片预览和姿态文字提示，重新采集会清空整组照片。

可以把首次使用串成一个有明确终点的流程：新员工和管理员都知道已经完成了什么、还差什么。

### 建议体验

**管理员视角：建档后直接进入下一步。**

员工创建成功后，在账号交付完成的基础上提示“接下来录入人脸”。人员列表可显示“待录入”“可进行体验验证”“已完成首次体验”等阶段，管理员可以从未完成步骤继续。

**员工视角：每次只需要完成一个动作。**

进入录入后，依次展示正脸、左侧、右侧的简短姿态示范。每张照片标明“待拍摄”“待检查”或“已通过”，检查状态对应实际结果。

某张需要重拍时，点击该缩略图重新拍摄，保留其余图像；最终提交时完成整组校验。这样用户能够清楚区分“照片已拍到”和“录入已通过”。

**结束时：让员工实际体验一次。**

录入成功后提供“体验一次打卡”的引导，明确这次为测试记录。若开发独立体验入口，将它限定为单次测试会话，避免为新员工体验而切换全局测试设置。

体验完成后显示“首次设置已完成”，并说明日常打卡入口和查看个人记录的位置。

### 体验创新点

将第一次使用设计成一段能够走完的引导流程。完成标准是员工亲自体验成功，并且知道以后如何使用。

### 演示方式

用一名新员工的完整流程展示：建档、账号交付、分步采集、单张补拍、测试体验、找到个人工作台。观察管理员需要额外口头解释多少次。

## 八、最推荐的组合与落地顺序

如果先做一套能够明显改善体验的版本，建议选择以下组合：

**连续引导打卡 + 失败原地处理 + 异常记录直接办理。**

它覆盖用户最常见的三种情况：正常完成、当场遇到问题、事后发现问题。三项之间相互衔接，也适合做成一段完整的项目演示。

| 阶段 | 优先完成的内容 | 用户获得的变化 |
| --- | --- | --- |
| 第一阶段 | 当前时段主操作、可视动作引导、明确成功回执、持续可见的失败帮助 | 打卡过程更容易理解，遇到问题知道怎么继续 |
| 第二阶段 | 异常直达补卡、预填明确字段、原记录跟踪进度 | 发现问题后能在原处办完 |
| 第三阶段 | 今天工作台、审批上下文、处理后跳转下一条 | 员工和管理员都少找页面、少重复核查 |
| 第四阶段 | 新员工引导、单张补拍、单次体验验证 | 首次使用更顺畅，管理员更容易带新人 |

部分体验需要补充接口信息，例如可用打卡时段、实际确认时间、动作阶段、记录与申请的关联，以及审批后的变化预览。开发时先让这些状态与真实业务结果一致，再组织页面展示。

界面设计可以统一遵循四条约定：

1. **每个步骤突出一个主要操作。** 让用户第一眼知道下一步。
2. **每个结果都能看懂。** 分清已完成、待确认、需要重试和等待处理。
3. **跨页面继续同一件事。** 带上日期、记录和筛选条件，返回时保留位置。
4. **用文字、图标共同表达状态。** 手机端优先大按钮和就近操作，语音作为可选择的辅助。

## 九、如何证明体验确实改善

找几位第一次接触项目的参与者，分别体验当前流程和改进流程，交替安排使用顺序。给出任务后先让他们独立完成，记录在哪一步停顿、求助或返回。

| 体验任务 | 观察重点 |
| --- | --- |
| 第一次完成上班打卡 | 是否选错类型，是否理解动作，是否知道已经成功 |
| 摄像头权限关闭后继续操作 | 能否找到解决方式，是否需要管理员口头指导 |
| 打卡中断后确认结果 | 能否区分待确认和失败，是否发生盲目重复操作 |
| 给昨天的缺签退提交补卡 | 切换页面次数、重复输入字段、完成耗时 |
| 查看补卡处理结果 | 能否从原记录找到进度并理解结论 |
| 管理员核查一条补卡申请 | 是否需要离开审批页面，能否判断批准后的影响 |
| 新员工完成第一次使用 | 中途求助次数，是否能独立找到日常入口 |

重点记录任务完成率、操作耗时、误操作次数、求助次数和用户原话。展示时可以将同一任务的前后操作路径并排放置，再补充实测结果。

项目演示可以采用一条连贯的故事：员工早晨跟随引导完成打卡，发现昨天缺签退后直接办理，管理员在完整上下文中审批，员工回到原记录看到结果。这样能完整呈现体验创新对日常使用的价值。
